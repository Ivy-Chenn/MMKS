    Embedded System Principle Knowledge

    An embedded system is a core control and information processing platform that connects robot algorithms, sensors, actuators, and external networks. During the operation of a robot, sensors continuously collect information about the robot's own status and the surrounding environment; SoCs and MCUs calculate and process this information, convert the decisions generated by algorithms into low-level control instructions, which are finally executed by actuators.Meanwhile, robots also need to exchange information with Apps, Cloud, RTK systems and other external devices via wireless connection methods such as 4G, Bluetooth, Wi-Fi and LoRa.

    From the perspective of the complete machine, a basic information chain of Sensor → SoC / MCU → Control → Actuator is formed inside the robot. After the Actuator performs an action, the robot's status and the surrounding environment change, and the Sensor acquires new information again and feeds it back to the system, thus forming a complete closed loop of Sensing → Processing → Decision → Control → Execution → Feedback.

    Meanwhile, the robot also connects to external systems via the App ↔ Cloud ↔ Robot architecture. The Cloud further supports IoT functions including Binding, OTA Upgrade, Map Backup, and Data Center. Therefore, the embedded system serves not only as a platform for algorithm operation but also as the core system connecting Sensors, Algorithms, Hardware, Communications, and the Cloud.

    This module is mainly divided into six chapters: Embedded System Architecture, SoC \& MCU, Sensor \& Actuator Interface, Internal Communication, Wireless Communication \& Connectivity, as well as IoT, Cloud \& App.

    Embedded System Architecture Complete Machine Embedded Architecture

    1.1 Basic Composition of Embedded Systems

    A robot does not have a single processor that directly performs all its functions; instead, it is composed of multiple functional modules with distinct roles. Based on the functions of each module in the system, the entire embedded system can be roughly categorized into Sensing, Computing, Control, Execution, and Connectivity components.

    Sensors serve as the information input terminals of the system, responsible for acquiring the robot's own status and surrounding environmental information, such as Bumper, Emergency Stop, LiDAR, Vision, Ultrasonic and other sensors or system statuses. SoCs and MCUs constitute the main Computing \& Control Platform of the robot, which processes the input information and generates corresponding algorithmic or control results.Actuator serves as the execution end of the system, such as Wheel Motor, Cutter Motor and Lift Motor, which is responsible for converting electronic control instructions into actual actions.

    Therefore, the most fundamental information relationship inside a robot can be expressed as follows:

    Sensor → SoC / MCU → Actuator

    However, robots do not operate in a unidirectional manner based on fixed instructions. After the Actuator performs an action, the robot's own state and the external environment change, and the Sensor will reacquire new information and feed it back to the control system. Therefore, a continuous feedback closed loop is formed during the actual operation:

    Sensor → Processing → Decision → Control → Actuator → Feedback

    1.2 Data Flow \& Control Flow

    When understanding robotic embedded systems, a further distinction can be made between Data Flow and Control Flow.

    Data Flow mainly describes how information enters the system from sensors. For example, a Camera generates Image Data, LiDAR produces environmental distance and geometric information, an IMU provides motion and posture data, while sensors such as Bumper and Emergency Stop deliver corresponding Trigger / Status Information. These data will be sent to the SoC or MCU according to functional and real-time requirements.

    Control Flow describes how control information is transmitted to the actuators after the system makes a decision. For example, after the Navigation Algorithm determines that the robot needs to move forward, the system needs to convert this High-Level Decision into low-level motion control commands, and then drive the Motor through the control system.

    Therefore, the complete process can be understood as follows:

    Sensor Data → Processing → Algorithm / Logic → Control Command → Actuator → Feedback

    This is also why a robot's function is usually not accomplished by a single sensor, algorithm or hardware alone, but relies on continuous data exchange between multiple modules.

    1.3 Relationship between Embedded System and Algorithm / Hardware

    The three modules, namely Algorithm, Embedded System and Hardware, are interrelated yet play distinct roles.

    Algorithm mainly addresses what a robot should do, such as determining its current location, selecting the appropriate navigation path, and judging whether obstacle avoidance is required;Embedded System is responsible for issues including where Sensor Data is processed, where the algorithm runs, how information is exchanged between different modules, and how Algorithm Decision is converted into control commands;Hardware provides the actual capabilities of perception, power supply, driving and execution.

    Therefore, the relationship among the three can be simply understood as follows:

    Sensor / Hardware → Embedded System → Algorithm → Embedded System → Hardware / Actuator

    Embedded System lies between Algorithm and Hardware, serving as the connection hub for the Data Flow and Control Flow of the entire machine.

    SoC \& MCU Computing and Control Platform

    2.1 Basic Concepts of SoC and MCU

    SoC (System on Chip) and MCU (Microcontroller Unit) are two crucial computing and Control Units inside a robot. Both are capable of running software and processing data, but they typically undertake different tasks.

    SoCs typically feature robust computing and data processing capabilities, making them better suited for running algorithms with heavy computational loads such as Vision, Localization, SLAM, Navigation, and AI Recognition. As such, an SoC can be understood as the High-Level Computing Platform of a robot.

    MCUs are better suited for handling low-level control tasks that demand high real-time performance and have relatively clear objectives, such as Sensor status reading, Motor Control, Actuator Control, and Safety Signal Monitoring. Therefore, an MCU can be regarded as the Real-Time Control Platform of a robot.

    The basic division of responsibilities between the two can be summarized as follows:

    SoC → Perception / Localization / Planning / High-Level Computing

    MCU → Sensor Monitoring / Real-Time Control / Actuator Control

    2.2 Why both SoC and MCU are required

    A high-performance SoC does not mean that robots no longer need MCUs, as these two types of processors address different types of problems.

    Cameras and LiDARs generate a large amount of environmental data, which requires relatively complex computation before being applied to vision, localization and environment understanding, making them more suitable to be processed by SoCs. The algorithm running on the SoC can determine the next movement of the robot based on environmental, map and localization information.

    However, "the robot should move forward" remains merely a High-Level Decision. When actually executing this action, the system also needs to continuously control the speeds of the left and right wheels, read Motor Feedback, monitor the Sensor State, and make constant adjustments based on the actual execution status. Such real-time control tasks are better suited for MCUs.

    Therefore, a typical information link can be understood as follows:

    Vision / LiDAR / Localization Data → SoC → Motion Decision → MCU → Actuator

    At the same time, the underlying state will feed back upward:

    Sensor / Actuator Feedback → MCU → SoC → Algorithm

    SoC and MCU connect High-Level Algorithm with Low-Level Control through continuous data exchange.

    2.3 Relationship between Different Sensors and SoC/MCU

    Not all sensor data must first enter the SoC. Depending on the data volume, processing method and real-time requirements, different sensors can be processed by either the SoC or the MCU.

    Sensors such as Camera and LiDAR generate a large amount of data, and usually need to participate in Vision, Localization, SLAM and Environment Perception, so they are mainly related to the high-level algorithms running on the SoC.

    Information provided by sensors such as Bumper and Emergency Stop is relatively simple, yet requires high response speed, so it can be processed quickly by the MCU or the corresponding real-time control system.

    It can be simply understood as:

    Complex Environment Data → SoC

    Real-Time Status / Control Signal → MCU

    The specific data path varies depending on the hardware architecture and functional design of different products.

    2.4 Product Evolution of SoC + MCU

    As the functions of robots continue to expand, the requirements for the Computing Platform of products are also rising. When the functions and Sensors of early products were relatively simple, MCUs could undertake more control tasks; with the addition of functions such as Vision, LiDAR, SLAM and Multi-Sensor Localization, the data volume and algorithm complexity have increased significantly, so it is necessary to introduce SoCs with stronger performance.

    The product computing platform can gradually evolve from an MCU-centric setup to SoC + MCU Architecture, and further upgrade the computing power of the SoC in line with algorithm requirements, for instance, advancing from the X3 platform to the X5 platform.

    However, in this process, MCUs have not been replaced by SoCs. The performance improvement of SoCs mainly supports more complex Perception and Algorithm Processing, while MCUs continue to be responsible for low-level real-time control and hardware management. Therefore, the development of product computing platforms essentially evolves from relatively simple control systems to a collaborative architecture of High-Level Computing + Real-Time Control.

    Sensor \& Actuator Interface: Perception Input and Actuation Output

    3.1 The Role of Sensors in Embedded Systems

    Sensor serves as the interface through which robots obtain information about their own status and the external environment. The Sensor itself is responsible for detecting and collecting information, while the SoC, MCU and Algorithm further process this data to determine how the robot should respond.

    Based on the actual functions of the robot, the relevant inputs can be simply understood as different types.

    Contact Sensor (Contact-type Sensor) is triggered by physical contact or changes in mechanical status, such as Bumper, Emergency Stop, and some types of Lift Detection. This type of Sensor usually provides relatively clear status information and is frequently involved in basic safety and status judgment.

    Non-contact Sensors do not require direct physical contact with the target, typical examples include vision sensors, LiDAR and ultrasonic sensors. They are primarily responsible for collecting information about the surrounding environment, and further support functions such as perception, localization and obstacle detection.

    The system may also contain Logic / Derived State formed based on one or more Sensor Signals. For example, the system can synthesize data from the Wheel, IMU and the robot's motion state to determine whether a Slip has occurred. Such states do not necessarily correspond to an independent physical Sensor, but may be results calculated by the system from multiple inputs.

    3.2 How Sensor Data Enters the System

    Different sensors generate data types and volumes that vary significantly. For example, a bumper may only need to report a Triggered / Not Triggered status, while a camera continuously generates large volumes of image data, and LiDAR continuously produces environmental distance and geometric information.

    Therefore, the processing paths for different Sensors may also vary:

    Simple State Sensor → MCU / Controller

    Vision / LiDAR → SoC → Perception Algorithm

    These pieces of information from different sources are ultimately further utilized by the Algorithm and Control System.

    Therefore, a normal Sensor does not necessarily mean that the final function is normal. A complete function usually needs to go through the following processes:

    Sensor → Data Transfer → Processing → Decision → Control

    Any abnormality in any of these links may eventually manifest as a functional failure of the robot.

    3.3 Actuator

    Actuator is responsible for converting electronic control instructions into actual physical actions. Typical actuators in robots include wheel motors, cutter motors, lift motors, and other motion execution mechanisms.

    Actuators are generally not directly controlled by high-level Algorithms, but are implemented through low-level control systems and Drivers. For example:

    Navigation Decision → Motion Command → MCU / Controller → Motor Driver → Wheel Motor

    After the Motor performs an action, its Speed, Current, Position or other status can be fed back to the control system again, thus forming Closed-Loop Control:

    Command → Actuator → Feedback → Controller → Adjustment

    Therefore, from a systematic perspective, it can be simply understood as follows:

    Sensor = What is happening?

    SoC / MCU = What should the system do?

    Actuator = Execute the action.

    Internal Communication

    4.1 Why Internal Communication Is Needed

    Inside a robot, there are components including SoC, MCU, Sensor, Driver, Battery/BMS, and other electronic modules. These modules do not operate independently of one another; instead, they require continuous exchange of data and control information.

    For example, after the SoC calculates the new Motion Decision, it needs to transmit the relevant information to the MCU; after the MCU completes the control operation, it needs to return the Hardware Status, Sensor State and Error Information to the SoC.

    Therefore, there is a large amount of two-way information exchange inside the robot:

    SoC ↔ MCU

    Controller ↔ Sensor

    Controller ↔ Driver / Actuator

    Internal Communication can be understood as the "information channel" between different electronic modules of a robot.

    4.2 Command、Status \& Feedback

    The information exchanged in internal communication can be simply divided into Command, Status and Feedback.

    A Command indicates what the control system expects another module to execute, such as Target Speed, Start/Stop, or other action requirements; a Status represents the current state of a module, such as Ready, Running, Stopped, or Error; while Feedback is used to inform the control system of the actual execution result, such as Actual Speed, Position, Current, or Sensor State.

    Therefore, a typical control process can be expressed as follows:

    Command → Module → Execution → Feedback → Controller

    Robots rely on this continuous exchange of information to determine whether an instruction has actually been executed, and decide whether further adjustments are necessary based on the feedback.

    4.3 Communication Exception

    When internal modules fail to exchange information properly, the corresponding function may not work normally even if the relevant Hardware itself is not damaged.

    For example, the SoC may have generated a correct Motion Decision, but if the control information fails to be properly transmitted to the MCU or the execution module, the robot may still exhibit "no action"; conversely, if the hardware has executed the action normally but the status cannot be fed back to the upper-level system, the upper-level system may also judge it as abnormal.

    Therefore, for a functional anomaly, it is necessary to distinguish between:

    Device / Hardware → Communication → Controller / Software

    That is to say:

    Hardware Exception ≠ Communication Exception

    Specific products may internally adopt different communication interfaces and protocols. For Distis/Dealers, the priority is not to master the underlying communication timing, but to understand that stable data communication between modules is required for them to jointly complete a function.

    Wireless Communication \& Connectivity

    Robots not only need to exchange data between their internal modules, but also need to establish connections with external devices such as Phone, Internet, Cloud, RTK Service or other external devices. Different Wireless Technologies are responsible for different types of information transmission.

    First, it is necessary to distinguish:

    Data Communication → Bluetooth / Wi-Fi / 4G / LoRa

    Positioning Signal → GNSS

    They can exist in a robot at the same time, but perform different functions.

    5.1 Bluetooth

    Bluetooth is mainly used for Short-Range Local Communication between a robot and nearby devices, such as establishing a local connection between a Smartphone and a Robot.

    Phone ↔ Bluetooth ↔ Robot

    Bluetooth is therefore more suitable for Nearby Connection, Configuration and Local Operation than for long-distance Cloud Connection.

    5.2 Wi-Fi

    Wi-Fi is primarily used for robots to connect to local networks, and further access the Internet and Cloud via a Router.

    Robot → Wi-Fi → Router → Internet → Cloud

    Special distinction is required:

    Wi-Fi Connected ≠ Internet Connected ≠ Cloud Connected

    Even if a robot is already connected to a Router, the relevant Cloud Function may still be unavailable if the Router does not have Internet access.

    5.3 4G

    4G/cellular networks provide wide-area internet connectivity for robots.

    Robot → 4G Network → Internet → Cloud

    Therefore, the robot does not need to be within the coverage of home Wi-Fi all the time to access the Remote / Cloud Service.

    In the NetRTK scenario, 4G can also undertake the network transmission of Correction Data, however:

    4G = Data Connection ≠ Positioning

    High-precision positioning still relies on GNSS Signal and effective RTK Correction Data.

    5.4 LoRa

    LoRa is a wireless technology designed for Long-Range + Low-Data-Rate Communication, which is suitable for transmitting small amounts of Status, Command or other Small Data Packet between devices.

    Device A ↔ LoRa ↔ Device B

    Therefore, its positioning is not completely the same as that of Wi-Fi / 4G:

    Wi-Fi / 4G → Internet / Cloud Connection

    LoRa → Long-Range Device-to-Device Communication

    The specific function that LoRa undertakes in robots needs to be determined according to the specific product architecture.

    5.5 GNSS

    GNSS differs from the preceding technologies. Bluetooth, Wi-Fi, 4G and LoRa are primarily responsible for Data Communication, while the core function of GNSS is Satellite Positioning.

    GNSS Satellites → GNSS Signal → Robot Receiver → Position

    GPS, Galileo, BeiDou, GLONASS and other systems all fall under the category of GNSS.

    GNSS, RTK and Communication Link need to be clearly distinguished:

    GNSS → Satellite Positioning

    RTK / NetRTK → Correction → Higher Positioning Accuracy

    4G / Wi-Fi / LoRa → Data Transmission（depending on product architecture）

    For example, NetRTK can utilize both GNSS and network communication simultaneously:

    Satellite → GNSS Signal → Robot RTK Service → Internet → Robot

    Both types of information ultimately participate in high-precision positioning together.

    IoT, Cloud \& App

    6.1 Basic Concepts of IoT

    IoT (Internet of Things) enables robots to exchange information with clouds, apps and backend services via the network.

    In a robotic system, the basic architecture can be understood as: App ↔ Cloud ↔ Robot

    Wherein:

    Robot → Executes tasks and generates Device Data ** Cloud → Connects Robot, User Account and Cloud Services ** App → Provides entry for user operation and device management

    Therefore, IoT is not an independent Hardware Module inside a robot, but a system consisting of:

    Robot + Connectivity + Internet + Cloud + App

    together form a system.

    6.2 Local Function \& Cloud Function

    Some functions of the robot can be implemented via Local Connection, while Remote Service usually requires the Internet and Cloud.

    It can be simply understood as:

    Local：Phone ↔ Robot

    Cloud：App ↔ Cloud ↔ Robot

    Therefore：Robot Connected ≠ Internet Available ≠ Cloud Service Available

    When troubleshooting issues, it is necessary to distinguish whether the fault occurs in Robot, Connectivity, Internet or Cloud Service.

    6.3 Binding

    Binding is used to establish: User Account ↔ Robot Identity

    the device affiliation relationship between them, which is usually managed by Cloud.

    Therefore, it can be understood as follows:

    User Account → Cloud ← Robot Identity ↓ Binding Relationship

    Binding essentially belongs to Device Management Logic, rather than Bluetooth/Wi-Fi itself.

    Therefore, when a device cannot be added by a new Account, it does not necessarily mean that there is a problem with the Robot Hardware or Wireless Communication, and the current Binding State should also be taken into consideration.

    6.4 OTA Upgrade

    OTA (Over-the-Air) Upgrade refers to the mechanism of delivering firmware updates to robots via the internet.

    The basic process is as follows:

    Firmware Package → Cloud → Robot → Firmware Update

    Robots may incorporate SoCs, MCUs and other electronic modules inside, so the firmware system may also consist of multiple components.

    Therefore, the normal operation of the system not only relies on Hardware, but also on the compatibility between different Software / Firmware Components:

    Hardware + Firmware + Communication → Stable System Operation

    Therefore, a Firmware-related Exception does not necessarily indicate Hardware Damage.

    6.5 Map Backup

    Mapping/SLAM is responsible for generating and updating maps, while the Cloud Service can take charge of the Backup/Synchronization of the generated Map Data.

    A clear distinction must be made between the two:

    Mapping / SLAM → Create / Update Map

    Cloud Service → Backup / Synchronize Map

    The basic data link can be understood as: Robot Map → Cloud → Backup / Synchronization

    6.6 Data Center

    During operation, the robot generates Status, Operation, Error, and Diagnostic Data and other types of information. Depending on the specific product design, some of these data may be uploaded to the Cloud / Data Center via the network for device status monitoring, issue analysis, and after-sales support.

    The basic link is as follows: Robot Data → Connectivity → Cloud / Data Center

    Essentially, the data displayed in the backend originates from the internal system of the Robot, and is then uploaded via the Network and Cloud Chain.

    Therefore：No Data in Cloud ≠ No Data Generated by Robot

    If there is no data in the backend, it is necessary to further determine where the problem occurs:

    Robot → Connectivity → Internet → Cloud / Data Center which link in the chain.

    Embedded System — Relationships Between Modules

    The core function of a robot embedded system is to connect Sensor, Algorithm, Control, Actuator, Communication and Cloud, enabling different modules to jointly realize the autonomous operation of the robot.

    Inside the robot, the Sensor first acquires its own status and environmental information: Sensor → SoC / MCU

    SoC is primarily responsible for high-level computing tasks such as Perception, Localization, SLAM and Navigation, while the MCU is mainly in charge of Sensor Monitoring, Real-Time Control and Actuator Control.The Decision generated by the Algorithm is further transmitted to the actuator through the control system: SoC → MCU / Controller → Actuator

    The execution result is then fed back again: Actuator / Sensor Feedback → MCU / SoC

    Therefore, the internal structure of a robot is formed as follows: Sensor → Processing → Decision → Control → Actuator → Feedback

    Different electronic modules continuously exchange data with each other via Internal Communication:

    Command ↔ Status ↔ Feedback ↔ Error Information

    Outside the robot, Bluetooth, Wi-Fi, 4G and LoRa provide data communication capabilities for different application scenarios, while GNSS offers Satellite Positioning Information: Robot ↔ Wireless Connectivity ↔ External Device / Internet

    At the IoT level, the following architecture is further formed: App ↔ Cloud ↔ Robot

    Cloud supports functions including Binding, OTA Upgrade, Map Backup, and Data Center.

    Therefore, from the perspective of the complete machine, the complete information relationship of the Embedded System can be summarized as follows:

    Environment / Sensor / GNSS → SoC \& MCU → Algorithm \& Control → Actuator → Robot State → Sensor Feedback

    同时：Robot ↔ Bluetooth / Wi-Fi / 4G / LoRa ↔ App / Cloud / External Service

    Understanding the significance of this system relationship lies in the fact that: an anomaly ultimately exhibited by a robot does not necessarily mean that the Hardware where the abnormal performance occurs is itself damaged. For a function to be executed from Sensor Input to the final implementation, it may sequentially go through Sensor, SoC/MCU, Internal Communication, Algorithm, Control and Actuator;A Cloud Function may further involve Wireless Connection, Internet, Cloud and Account.

    Therefore, when analyzing issues related to Embedded Systems, you can follow the sequence of Input → Processing → Communication → Control → Execution → Feedback to identify which stage the problem occurs in, so as to provide a systematic basis for subsequent troubleshooting.
